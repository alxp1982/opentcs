# Transport Orders — Configuration and Operations Guide

> Generated from code at [`742b0e6d`](https://github.com/alxp1982/opentcs/commit/742b0e6df9ccbabc660e585a85e55d585c0642fc) · fact coverage 100.0% · 42 verified claims

## What this feature does

This feature manages the creation, assignment, withdrawal, and querying of transport orders within the plant model . Host systems define transport destinations and parameters, track order lifecycles and historical events, and assign routes to automated vehicles . External dispatching workflows can trigger assignment runs, request immediate assignments to designated vehicles, or withdraw orders during execution .

## Settings and defaults

| Setting / input | Default | Effect | Notes |
|---|---|---|---|
| `type` | `"-"` | Sets the transport order category . | Represents no specific type when omitted . |
| `immediate` | None / not specified | Sets immediate withdrawal when `true`, or non-immediate withdrawal otherwise . | Query parameter when withdrawing an order . |
| `vehicle` | Omitted | Sets the intended vehicle to the named vehicle, or clears the intended vehicle when omitted . | Query parameter when updating an order's intended vehicle . |

## Operating procedures

### 1. Create a transport order

1. Prepare a JSON payload containing at least a destination list . Each destination requires a destination location name and operation, and accepts an optional list of properties where each property consists of a required key and optional value .
2. Optionally supply additional configuration fields including dispensability, deadline, intended vehicle, peripheral reservation token, wrapping sequence, incomplete name flag, order type, order properties, and dependencies .
3. Ensure every destination targeting a point references an existing point in the plant model and specifies either a `MOVE` or `PARK` operation .
4. Ensure every destination targeting a location references an existing location in the plant model and specifies an operation that is either `NOP` or allowed by both the location type and at least one attached link .
5. If assigning the order to a wrapping sequence, verify that the order type matches the allowed sequence types or that the sequence permits any type (`*`) .
6. Submit the creation request with the order name . A successful request returns the created transport order details as JSON .

### 2. Update an intended vehicle

1. Identify the target transport order by name . Verify that the order is currently in `RAW`, `ACTIVE`, or `DISPATCHABLE` state .
2. To assign an intended vehicle, submit the update request with the target vehicle name . Ensure the specified vehicle exists in the model .
3. To clear an existing intended vehicle assignment, submit the update request omitting the vehicle name .

### 3. Trigger immediate vehicle assignment

1. Identify the transport order by name .
2. Ensure the order exists in the model .
3. Submit the immediate assignment request to route the order directly to its designated vehicle .

### 4. Trigger a general dispatcher run

1. Submit a dispatcher trigger request .
2. The dispatcher evaluates assignments across the plant model and responds with an empty success confirmation .

### 5. Withdraw a transport order

1. Identify the transport order by name . Ensure the order exists in the model .
2. Choose whether to perform an immediate or non-immediate withdrawal .
3. Choose whether to disable the assigned processing vehicle: if requested and a processing vehicle is assigned, the vehicle's integration level updates to `TO_BE_RESPECTED`, reserving resources without allowing new order assignments .
4. Submit the withdrawal request via the dispatcher .

### 6. Query transport orders

1. To retrieve a single transport order, query by the order name . The response details the order name, dispensability flag, type, state, destinations, drive orders, current drive order and route step indices, creation, deadline, and completion timestamps, history, dependencies, vehicle assignments, peripheral reservation tokens, wrapping sequence, and properties .
2. To retrieve all orders, query the collection . Results are returned sorted by name in ascending order .
3. To filter orders by intended vehicle, provide the vehicle name parameter . Ensure the vehicle exists in the model .

## Interactions and gotchas

- **Withdrawal vehicle disabling**: When withdrawing an order with the vehicle disabling flag set to true and a processing vehicle is assigned, the vehicle's integration level updates to `TO_BE_RESPECTED` . At this level, the vehicle reserves resources without allowing order assignment .
- **Intended vehicle update timing**: Updating or clearing an intended vehicle is only permitted while an order is in `RAW`, `ACTIVE`, or `DISPATCHABLE` state . Once an order enters `BEING_PROCESSED`, `WITHDRAWN`, `FINISHED`, `FAILED`, or `UNROUTABLE`, changes are rejected .
- **Wrapping sequence order types**: Orders attached to a wrapping sequence must match the sequence's permitted order types unless the sequence explicitly allows any type (`*`) .
- **Point versus location operations**: Operations on destination points are restricted to `MOVE` and `PARK` . Operations on locations must be `NOP` or must be explicitly allowed by both the destination's location type and at least one attached link .

## Troubleshooting

| Symptom | Cause | Resolution |
|---|---|---|
| HTTP 400 Bad Request on order creation | Malformed JSON in the request body . | Validate JSON syntax before resubmitting the request . |
| HTTP 400 Bad Request on order creation | A point destination specified an operation other than `MOVE` or `PARK` . | Change the point destination operation to `MOVE` or `PARK` . |
| HTTP 400 Bad Request on order creation | A location destination specified an operation that is neither `NOP` nor allowed by both the location type and at least one attached link . | Configure an operation permitted by both the location type and attached link, or use `NOP` . |
| HTTP 400 Bad Request on order creation | An order type does not match the wrapping sequence's allowed types and the sequence does not allow any type (`*`) . | Align the order type with sequence rules or allow any type on the sequence . |
| HTTP 400 Bad Request on vehicle update | The order is not in `RAW`, `ACTIVE`, or `DISPATCHABLE` state . | Verify the order status before attempting to reassign or clear the intended vehicle . |
| HTTP 400 Bad Request | An invalid argument was passed in the request . | Correct the invalid parameter in the request payload or URL . |
| HTTP 404 Not Found on order creation | A destination references a location or point name that does not exist in the plant model . | Verify that all referenced point and location names exist in the plant model . |
| HTTP 404 Not Found on order retrieval, update, assignment, or withdrawal | No transport order exists with the specified name . | Verify the transport order name against existing orders . |
| HTTP 404 Not Found on vehicle update or order query | The vehicle specified in the query parameter does not exist . | Verify that the vehicle name exists in the plant model . |
| HTTP 404 Not Found | A referenced kernel model object does not exist . | Ensure all referenced model entities exist prior to issuing the request . |
| HTTP 409 Conflict | The object being created already exists . | Supply a unique name for the new object . |
| HTTP 500 Internal Server Error on order creation | Response serialization to JSON failed . | Check server logs for serialization errors . |
| HTTP 500 Internal Server Error during dispatcher or order requests | Kernel execution was unexpectedly interrupted, encountered an illegal state, or experienced an underlying execution failure wrapped as a kernel runtime exception . | Inspect kernel operational logs to diagnose runtime failures or thread interruptions . |

- When filtering the transport orders collection by `intendedVehicle`, the API responds with HTTP 404 if the vehicle does not exist . Published docs do not state that an unknown vehicle parameter returns HTTP 404 .

- An omitted transport order type defaults to `"-"` . Published docs do not document this default value .
- Requesting immediate assignment returns HTTP 404 if the transport order does not exist . Published docs do not document this HTTP 404 response .
- Requesting an order withdrawal returns HTTP 404 if the transport order does not exist . Published docs do not document this HTTP 404 response .
- Retrieving an unknown transport order returns HTTP 404 . Published docs do not document this HTTP 404 response .
- Submitting malformed JSON on transport order creation returns HTTP 400 . Published docs do not document this HTTP 400 response .
- Specifying an unknown destination point or location on order creation returns HTTP 404 . Published docs do not document this HTTP 404 response .
- Specifying an invalid point operation (not `MOVE` or `PARK`) or an invalid location operation returns HTTP 400 . Published docs do not document these HTTP 400 responses .
- Adding an order to a wrapping sequence with a mismatched order type returns HTTP 400 . Published docs do not document this HTTP 400 response .
- Updating an intended vehicle returns HTTP 404 if either the transport order or the vehicle does not exist . Published docs do not document these HTTP 404 responses .
- Internal runtime exceptions such as `IllegalStateException` and `KernelRuntimeException` are mapped globally to HTTP 500 . Published docs do not document these global exception mappings .
