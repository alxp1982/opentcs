# Transport Orders — Product Requirements

> Generated from code at [`742b0e6d`](https://github.com/alxp1982/opentcs/commit/742b0e6df9ccbabc660e585a85e55d585c0642fc) · fact coverage 100.0% · 51 verified claims

## Summary
Transport orders define tasks and movement sequences dispatched to automated guided vehicles and other carriers . Users can submit new transport orders with dedicated destinations, manage assignments to intended vehicles, trigger dispatching runs, withdraw orders, and query order states and execution history . This capability enables host systems to direct automated workflows, monitor vehicle progress through individual drive orders, and intervene dynamically when operational plans change .

## What users can do

### Create a transport order
Users create a transport order by providing an order name and a list of destination specifications . Each destination requires a destination location name and an operation, along with optional custom properties . Creation requests can optionally supply flags for incomplete names or dispensability, a deadline, an intended vehicle, peripheral reservation tokens, a wrapping order sequence, an order type, custom properties, and order dependencies . If no order type is provided, the system assigns a default type of "-" .

The system rejects creation if destination locations or points do not exist in the plant model . Destination operations are validated: point destinations must use either "MOVE" or "PARK", while location destinations must specify "NOP" or an operation permitted by both the location type and at least one attached link . If the order belongs to a wrapping sequence, its type must match the sequence's allowed types unless the sequence allows any type ("*") .

### Retrieve transport orders
Users can inspect an individual transport order by name or retrieve a list of all transport orders . Retrieved lists are sorted by order name in ascending order . Users can filter the list to only include orders intended for a specific vehicle . If the requested transport order or the specified intended vehicle cannot be found, the system rejects the query .

Responses contain full order details, including dispensability, type, current state, destinations, drive orders, current route step and drive order indices, creation, deadline, and finished timestamps, historical event entries, dependencies, intended and processing vehicles, peripheral reservation tokens, wrapping sequences, and properties .

### Update the intended vehicle
Users can set or clear the intended vehicle for an existing transport order . Providing a vehicle name assigns that vehicle as intended, while omitting it clears the assignment . The request is rejected if the transport order does not exist, if the specified vehicle does not exist, or if the transport order is not in an incomplete, submitted, or dispatchable state .

### Assign a transport order immediately
Users can request that the dispatcher immediately assign a transport order to its intended vehicle . The system rejects the request if the referenced transport order does not exist .

### Withdraw a transport order
Users can withdraw a transport order via the dispatcher, with an option to execute the withdrawal immediately or non-immediately . When requested, the system can also update the assigned processing vehicle's integration level to reserve resources without accepting new orders . The request is rejected if the named transport order does not exist .

### Trigger dispatching
Users can manually trigger a dispatcher run to assign available transport orders to vehicles .

## States and lifecycle
A transport order progresses through the following lifecycle states:
- RAW: The order is incomplete .
- ACTIVE: The order has been submitted .
- DISPATCHABLE: The order's dependencies are satisfied and it is eligible for assignment .
- BEING_PROCESSED: The order is assigned to a vehicle and currently executing .
- WITHDRAWN: Processing was aborted .
- FINISHED: The order completed successfully .
- FAILED: The order execution failed .
- UNROUTABLE: No route could be planned for the order .

Drive orders and drive order destinations reflect execution through five states: PRISTINE, TRAVELLING, OPERATING, FINISHED, and FAILED .

## Business rules
- A property consists of a required key string and an optional string value .
- When defining a destination in a creation request, a destination location name and operation are required, with an optional list of properties .
- A destination state tracks the destination's location name, operation, property list, and execution state .
- A planned route contains total routing costs and an ordered sequence of route steps .
- Each route step defines the source point, destination point, connecting path, vehicle orientation (FORWARD, BACKWARD, or UNDEFINED), route index, costs, execution allowance flag, and optional rerouting type (REGULAR or FORCED) .
- A drive order destination specifies the destination point or location name, the operation to perform, and properties .
- Object history entries record an event timestamp, an event code, and supplemental details .
- Kernel object events classify modifications as created, modified, or removed .
- A vehicle's integration level controls kernel participation: ignored (position ignored), noticed (position tracked without resource reservation), respected (resources reserved), or utilized (order assignment allowed) .

## Glossary
- **Destination State**: A description of a drive order destination, including its location name, operation, properties, and execution state .
- **Drive Order**: A component of a transport order reporting the drive order name, destination details, parent transport order name, planned route, and execution state .
- **Integration Level**: The level defining a vehicle's participation in kernel operations, ranging from ignored, noticed, respected, to utilized .
- **Object History**: An ordered record containing historical event entries for an object .
- **Property**: A key-value pair containing a required key string and an optional value string .
- **Route**: A path execution plan containing total routing costs and an ordered list of route steps .
- **Route Step**: A movement segment within a route defining source and destination points, connecting paths, orientation, costs, execution permissions, and rerouting type .
- **Transport Order**: An order composed of destinations, drive orders, dependencies, and execution constraints assigned to vehicles .

## Requirements
- TO-A1: The system shall create a transport order with a specified name and destination list .
- TO-A2: The system shall accept optional creation parameters including incomplete name flags, dispensability flags, deadlines, intended vehicles, peripheral reservation tokens, wrapping sequences, types, properties, and order dependencies .
- TO-A3: The system shall default the transport order type to "-" when omitted .
- TO-A4: The system shall reject creation if a destination references a nonexistent location or point in the plant model .
- TO-A5: The system shall reject creation if a point destination specifies an operation other than "MOVE" or "PARK" .
- TO-A6: The system shall reject creation if a location destination specifies an operation that is neither "NOP" nor allowed by the location type and at least one attached link .
- TO-A7: The system shall reject creation if adding an order to a wrapping sequence whose allowed types do not include the order type and do not permit any type .
- TO-B1: The system shall retrieve an individual transport order by its name .
- TO-B2: The system shall retrieve all transport orders sorted by name in ascending order .
- TO-B3: The system shall filter retrieved transport orders by the specified intended vehicle .
- TO-B4: The system shall reject order retrieval requests when the transport order or intended vehicle does not exist .
- TO-C1: The system shall update the intended vehicle of a transport order to the specified vehicle .
- TO-C2: The system shall clear the intended vehicle of a transport order when no vehicle is specified .
- TO-C3: The system shall reject intended vehicle updates if the order does not exist, the vehicle does not exist, or the order is not in RAW, ACTIVE, or DISPATCHABLE state .
- TO-D1: The system shall request immediate assignment of a transport order to its intended vehicle .
- TO-D2: The system shall reject immediate assignment requests when the transport order does not exist .
- TO-E1: The system shall withdraw a transport order via the dispatcher .
- TO-E2: The system shall support immediate and non-immediate withdrawal requests .
- TO-E3: The system shall update the assigned processing vehicle's integration level to TO_BE_RESPECTED when vehicle disabling is requested during withdrawal .
- TO-E4: The system shall reject withdrawal requests when the transport order does not exist .
- TO-F1: The system shall trigger a dispatcher run to assign transport orders .

## Open items
- Published docs state that a property value is required, but the code allows the property value to be optional .
- Published docs state that destination states include ACTIVE, whereas the code defines destination states as PRISTINE, TRAVELLING, OPERATING, FINISHED, and FAILED .
