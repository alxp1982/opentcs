# Vehicles — Product Requirements

> Generated from code at [`742b0e6d`](https://github.com/alxp1982/opentcs/commit/742b0e6df9ccbabc660e585a85e55d585c0642fc) · fact coverage 85.9% · 80 verified claims

## Summary
The Vehicles capability allows users and external systems to monitor vehicle status, compute paths, control communication adapters, adjust operational parameters, and manage active vehicle assignments. Users can inspect vehicle poses, energy levels, and assigned transport orders, trigger route calculations avoiding designated resources, and pause or resume vehicle operations. In addition, callers can attach and enable vehicle communication adapters, send custom adapter messages, adjust integration levels and envelope keys, update acceptable order types and energy thresholds, reroute in-transit vehicles, or withdraw active assignments.

## What users can do

### Retrieve vehicle information
Users can query all vehicles in the system sorted by name in ascending order, optionally filtering the results by vehicle processing state.  Users can also retrieve detailed status and attributes for a specific vehicle by name, including positions, orientations, energy thresholds, resource claims, and order assignments.  If a requested vehicle does not exist, or if an invalid vehicle processing state is provided as a filter, the request is rejected.

### Calculate routes
Users can compute vehicle routes from a starting point to one or more destination points, optionally identifying plant model resources to avoid.  When a starting point is omitted, the system defaults to using the vehicle's current position; the number of computed routes per destination point defaults to one when not specified.  The system rejects calculation requests if the vehicle does not exist, if the source point is omitted and the vehicle has no known position, or if any referenced source, destination, or avoided resource cannot be found.

### Manage communication adapters
Users can inspect adapter attachment details, attach a new communication adapter driver, enable or disable the adapter, and transmit custom messages to the driver.  When attaching an adapter, the system terminates and disables any existing adapter before initializing the new one, and records the factory property on the vehicle.  Requests fail if the vehicle does not exist, if the specified adapter description does not match an available adapter, or if no internal vehicle entry is found.

### Control vehicle movement and integration
Users can pause or resume a vehicle, change its integration level, or withdraw assigned transport orders.  When withdrawing an order, cancellation defaults to non-immediate unless specified, and setting vehicle disabling updates the integration level to be respected by traffic management.  The system rejects modifications if the vehicle does not exist, or if a user attempts to ignore or merely notice a vehicle while it is actively processing an order.

### Reroute vehicles
Users can request that a vehicle be rerouted along its route.  Rerouting defaults to regular rerouting respecting existing allocations, but callers can request forced rerouting from the vehicle's current position regardless of allocations.  The system rejects reroute requests if the vehicle does not exist, or if a forced rerouting is requested when the vehicle's position is unknown or immediate resource allocation fails.

### Configure vehicle operational profiles
Users can set envelope keys, acceptable order types, and energy level threshold sets.  Updating allowed order types configures each specified order type with a priority of zero, whereas updating acceptable order types accepts custom priorities.  Requests are rejected if the vehicle does not exist, if energy percentage thresholds are not between 0 and 100 inclusive, or if the envelope key is modified while the vehicle is processing an order or claiming/allocating resources.

### Trigger dispatching
Users can explicitly trigger a dispatcher execution run to evaluate and assign transport orders across the fleet.

## States and lifecycle
A vehicle processing state indicates whether a vehicle is IDLE, AWAITING_ORDER, or PROCESSING_ORDER.  An integration level determines whether a vehicle is ignored (TO_BE_IGNORED), displayed without impacting traffic (TO_BE_NOTICED), or respected by traffic management (TO_BE_RESPECTED).

## Business rules
- Angle properties support degrees and radians, length properties support millimeters, centimeters, meters, and kilometers, speed properties support kilometers per hour, meters per second, and millimeters per second, and percent properties support percent.
- Driving course blocks restrict resource usage either to a single vehicle at a time or to multiple vehicles traveling in the same direction.
- Vehicle driving orientation along a route is classified as forward, backward, or undefined.
- Route step calculations define source point, destination point, connecting path, and vehicle orientation.
- Energy thresholds configure critical, good, sufficiently recharged, and fully recharged percentage values, each constrained between 0 and 100 inclusive.
- A vehicle bounding box defines length, width, height, and a 2D reference offset.
- Updating vehicle pause state or integration level emits model modification events.

## Glossary
- **Acceptable Order Type**: A transport order type name coupled with a dispatching priority accepted by a vehicle.
- **Bounding Box**: A three-dimensional vehicle footprint describing length, width, height, and reference offsets.
- **Communication Adapter**: A driver attached to a vehicle that translates communication between the control system and the physical vehicle.
- **Envelope Key**: An identifier defining the vehicle envelope profile used for resource reservations.
- **Integration Level**: The operational tier of an entity indicating if it is ignored, noticed, or respected by traffic management.
- **Processing State**: The operational dispatching status of a vehicle (IDLE, AWAITING_ORDER, or PROCESSING_ORDER).
- **Rerouting Type**: The strategy used when recomputing vehicle paths, either regular (preserving resource allocations) or forced (recomputing from current position disregarding allocations).

## Requirements
- VEH-A1: The system shall retrieve all vehicles sorted by vehicle name in ascending order.
- VEH-A2: The system shall filter vehicle list results by processing state when specified.
- VEH-A3: The system shall reject vehicle listing queries when an invalid processing state filter is provided.
- VEH-A4: The system shall retrieve full status details for a named vehicle.
- VEH-A5: The system shall reject queries for vehicle status when the named vehicle does not exist.
- VEH-B1: The system shall compute routes from a source point to destination points while avoiding specified resources.
- VEH-B2: The system shall default the source point to the vehicle's current position when not specified.
- VEH-B3: The system shall default the maximum routes per destination point to one when omitted.
- VEH-B4: The system shall reject route calculation if the vehicle does not exist.
- VEH-B5: The system shall reject route calculation if the source point is omitted and the vehicle has no known position.
- VEH-B6: The system shall reject route calculation if the source point, any destination point, or any avoided resource is not recognized.
- VEH-C1: The system shall retrieve communication adapter attachment information for a named vehicle.
- VEH-C2: The system shall reject communication adapter information requests if the vehicle does not exist.
- VEH-C3: The system shall attach a specified communication adapter to a named vehicle, terminating and disabling any previous adapter.
- VEH-C4: The system shall reject adapter attachment if the vehicle does not exist or the adapter description does not match available adapters.
- VEH-C5: The system shall enable or disable a vehicle's communication adapter.
- VEH-C6: The system shall reject adapter enablement changes if the vehicle does not exist or has no entry.
- VEH-C7: The system shall transmit custom messages with parameters to a vehicle's communication adapter.
- VEH-C8: The system shall reject custom messages if the vehicle does not exist.
- VEH-D1: The system shall set the paused state of a named vehicle and emit modification events.
- VEH-D2: The system shall reject pause updates if the vehicle does not exist.
- VEH-D3: The system shall update a vehicle's integration level and emit modification events.
- VEH-D4: The system shall reject integration level updates to ignored or noticed states while the vehicle is processing an order.
- VEH-D5: The system shall reject integration level updates if the vehicle does not exist.
- VEH-D6: The system shall withdraw a vehicle's active transport order, defaulting immediate withdrawal and vehicle disabling to false.
- VEH-D7: The system shall reject order withdrawal if the vehicle does not exist.
- VEH-E1: The system shall trigger rerouting for a named vehicle, defaulting to regular rerouting unless forced rerouting is requested.
- VEH-E2: The system shall reject rerouting if the vehicle does not exist.
- VEH-E3: The system shall reject forced rerouting if the vehicle's position is unknown or immediate resource allocation fails.
- VEH-F1: The system shall update vehicle allowed order types with priority zero.
- VEH-F2: The system shall reject allowed order type updates if the vehicle does not exist.
- VEH-F3: The system shall update vehicle acceptable order types and their priorities.
- VEH-F4: The system shall reject acceptable order type updates if the vehicle does not exist.
- VEH-F5: The system shall update vehicle energy level threshold sets when values are between 0 and 100 inclusive.
- VEH-F6: The system shall reject energy threshold updates if the vehicle does not exist or threshold values are out of bounds.
- VEH-F7: The system shall update a vehicle's envelope key.
- VEH-F8: The system shall reject envelope key updates if the vehicle does not exist or is currently processing orders or claiming/allocating resources.
- VEH-G1: The system shall trigger a dispatcher run and return success upon completion.
